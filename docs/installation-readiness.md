# DSC 설치 전 준비와 당일 인수 절차

목표는 사무실 NAS 설치 직후 실제 CCTV·현장 엣지·사무실 수신기·AWS 조회·라이브 시청을 차례로 연결하는 것이다. 저장소에는 실행 코드, Docker 설정, 분석 프로그램 계약·목업, 장애 재현, 사전 점검 및 검수 기록 절차를 준비한다. 실제 장비·회선·등록값이 필요한 칸은 미확정으로 남기고, 로컬 성공을 현장 인수 완료로 바꾸지 않는다.

## 현재 확인된 사실

| 항목 | 확인한 내용과 근거 |
|---|---|
| CCTV | 이전 대화에서 Hikvision DS-2CD2186G2-I, 192.168.1.64, 메인 RTSP 101 수신·H.264 약 25초 녹화 |
| 임시 현장 PC | 맥북, 카메라 연결 유선 주소 192.168.1.10. Docker 파일 보존 시험 기록 있음 |
| 분석 프로그램 | 이준녕 담당 프로그램이 미완성이라는 이전 대화. 완료 전 기존 producer 목업 사용 |
| AWS 이력 | 11월 11일 v1.2 개발 스택 검증 기록. 현재 소스 v1.3 배포 완료로 승계하지 않음 |
| NAS | 11월 23일 주 설치 예정이라는 사용자 안내. 모델·볼륨·공유 방식은 현장 확정 필요 |
| 운영 제한 | 기존 AWS 개발 ClipAuditMode=synthetic 기록. 실제 CCTV 업로드 전 적절한 감사·배포 설정 확인 |

현재 회선 연결·카메라 설정을 바꾸거나 관리자 비밀을 추출하지 않는다. 카메라·NAS·M2M 비밀은 채팅·Git·문서에 넣지 않고 설치 호스트의 보호 파일로 공급한다. 이전 시험 영상과 사용자 미커밋 Word 원본은 보존한다.

설치 때 카메라·현장 PC·NAS·사무실 PC의 NTP와 시각 오차를 확인한다. 이벤트와 클립 메타데이터는 시간대가 있는 UTC로 기록하고, 카메라 OSD의 한국 시각은 UTC로 환산해 대조한다. 시계가 맞지 않으면 토큰·인증서 검증과 촬영부터 표시까지의 지연 측정이 틀릴 수 있으므로 허용 오차와 실제 측정값을 검수 기록에 남긴다.

## 설치 전에 채울 등록표

| 담당 | 확정할 값 | 완료 증거 |
|---|---|---|
| 현장 운영 | 최종 PC Linux·CPU·Docker, SSH 계정·키 경로, 카메라 LAN과 인터넷 경로 | 비밀 없는 장비·접속 목록 |
| 네트워크 | 현장↔사무실 VPN 주소·ACL, 현장→AWS 독립 회선, HTTPS DNS·인증서 | 포트·방향·허용 주체 표 |
| NAS 담당 | 모델·OS·파일시스템·공유 프로토콜, 볼륨 ID, 서비스 전용 루트·계정 | 마운트와 볼륨 마커, fsync·hard link 확인 |
| 백엔드 담당 | siteId·assetId, CCTV·로봇·archive별 client와 큐, 활성 주체·권한 | 실제 등록 매니페스트·scope 표 |
| 분석 담당 | inbox·클립 루트, 이벤트 코드·식별 지속성·녹화 완료·정리 소유자 | producer-integration-contract 확인 및 실제 파일 예제 |
| 서비스 담당 | 라이브 직원 범위·동시 카메라와 인원·허용 지연·로그인 URL | 승인한 성능 목표와 시청 원점 |
| 운영 담당 | 하루 클립 생성량·30일 및 장애 누적 용량·백업·경보 수신자 | 용량 산정과 복구 목표 |

실제 마운트가 분리되지 않으면 별도 볼륨임을 가장하는 마커를 빈 호스트 디렉터리에 만들지 않는다. NAS가 프로세스 실행이나 요구 파일 기능을 지원하지 않으면 지원 Linux 사무실 호스트·파일시스템 구성을 먼저 정한다. 보관 30일은 용량 상한이 아니며 원본과 관리 사본을 같은 디스크에 둘 때 둘 다 계산한다.

## 재현 가능한 설치 묶음

scripts/build_install_bundle.py가 승인한 코드·예제·문서를 모으고 파일별 SHA-256을 작성한다. 출력 경로는 새 디렉터리여야 한다. 비밀·실제 영상·로컬 DB·Office 잠금 파일·가상 환경·사용자 미커밋 문서는 포함하지 않는다. 이미지 빌드에 네트워크가 필요한 현장은 대상 CPU 이미지를 미리 빌드하고 별도 docker save와 해시로 반입한다. 아키텍처별 이미지를 실제 장비에서 검수한다.

```sh
python scripts/build_install_bundle.py runtime/install-ready/NEW_RUN
```

현장 field는 deploy/edge/compose.field.yaml, 사무실 receiver·archive는 deploy/edge/compose.office.yaml, 라이브는 deploy/streaming/compose.yaml을 사용한다. live와 field는 상태 디렉터리를 공유하지 않는다. 사무실 receiver와 archive는 기존 계약대로 같은 상태·NAS 루트를 사용한다. 설치 명령·HTTPS·복구는 office-worker-operations.md, 실시간은 streaming-installation-guide.md를 따른다.

## 사전 점검 실행

설정 파일은 실제 호스트 경로로 준비한다. preflight는 환경 모델, 비밀 파일 권한, 경로 존재와 카메라 설정 형식을 검사한다. --network는 카메라 TCP 접속만 확인하므로 인증·코덱·실제 프레임 검증은 별도다. 결과에는 비밀·상세 경로를 출력하지 않는다. 출력 파일은 새 이름이어야 한다.

```sh
PYTHONPATH=src python -m dsc.devtools.preflight \
  --field-env /etc/dsc/field.env \
  --office-env /etc/dsc/office.env \
  --output runtime/preflight-config.json
```

라이브는 --live-env와 --installation을 사용할 수 있다. 컨테이너용 환경 파일을 호스트에서 검사하면 컨테이너 경로가 없어서 실패할 수 있으므로 같은 bind mount 안에서 실행한다. NAS가 준비되면 실제 볼륨을 마운트하고 마커를 확인한 뒤 아래를 실행한다. 임시 전용 디렉터리에 4KiB 기록·파일 fsync·hard link 확정·디렉터리 fsync·읽기를 수행하고 자기 시험 파일만 정리한다. 기존 클립·manifest·outbox는 열지 않는다.

```sh
PYTHONPATH=src python -m dsc.devtools.preflight \
  --nas-root /mnt/dsc-archive \
  --volume-id ACTUAL_VOLUME_ID \
  --output runtime/preflight-nas.json
```

파일 기능 시험 성공만으로 정전 복구·NAS 디스크 영속성·실제 마운트 장치 정체성·백업 복원을 완료 판정하지 않는다. 디스크·전원 시험은 업무 데이터가 없는 검수 영역과 중단 범위를 합의한 뒤 진행한다.

## 설치 당일 진행 순서

1. 기존 개발·현장 데이터를 백업하고 버전·환경·용량을 기록한다. 새 DB 마이그레이션과 runtime grants를 적용하고 이전 이벤트·연결·클립 건수·해시를 대조한다. 새 라이브 기능은 설치가 끝날 때까지 비활성으로 둔다.
2. NAS 마운트·볼륨 마커·계정·저장 루트·파일 기능을 확인하고 사무실 수신 HTTPS와 워커를 설치한다. NAS 관리·SMB·NFS 포트를 인터넷에 열지 않는다.
3. CCTV field를 설치하고 producer 목업으로 이벤트와 실제 녹화 클립을 로컬 접수한다. 기존 개발 환경이 합성 전용이면 실제 영상을 업로드하지 말고 합성 클립으로 AWS 경로를 먼저 확인한다. 실제 영상 시험 환경의 감사·보관·권한을 준비한 뒤 전환한다.
4. 현장 관리 사본 → 사무실 NAS 확정 → STORED 보고를 확인한다. 원본·현장 사본·NAS 사본의 크기·SHA-256을 대조한다. accepted 이동은 로컬 접수이며 AWS 영속 저장은 outbox ACKED로 확인한다.
5. 허용 직원의 이벤트·시계열·AAS 조회 → 클립 요청 → 사무실 claim·S3 검증 → READY·직접 다운로드를 확인한다. 다운로드 파일을 원본과 대조하고 다른 센터·미허용 자산 접근을 거부하는지 확인한다.
6. NAS·사무실 워커·회선 장애와 ACK 유실을 각각 재현한다. 현장 예비 업로드·단일 lease·오래된 완료 거부·중복 복구·미확인 파일 보존을 확인한다. 현장→AWS 경로가 사무실 장애와 독립인지 확인한다.
7. 회사 VPN·TLS·Cognito callback·카메라 등록을 맞춘 뒤 라이브를 활성화한다. 시청 시작·종료·토큰 만료·권한 회수·영상 중단 안내·재연결을 사무실 PC에서 검수한다.
8. 분석 프로그램이 준비되면 동일 inbox 계약으로 목업을 교체하고 실제 이벤트·녹화 완료·중복·재시작을 다시 확인한다. 분석이 미완성이면 서비스 전체 운영 인수를 완료 처리하지 않는다.

## 인수 기록과 운영 시작 기준

실행마다 acceptance-report-template.md를 복사하고 실제 일시·장비·소스 버전·AWS 버전·입력·기대·실제·증거·판정을 남긴다. AT01~AT25에 AT26~AT30을 추가해 기록한다. 클립·이벤트·AAS와 라이브 각각의 권한·성능·복구를 대조한다. 사용자 토큰·RTSP 계정·서명 URL 원문·고객 영상은 보고서에 첨부하지 않는다.

| 경계 | 운영 시작 전 필요한 증거 |
|---|---|
| 데이터 무결성 | 이벤트 원자 저장·중복·재시작·NAS 확정·S3 해시·단일 lease |
| 인증과 권한 | 실제 Cognito, 주체·센터·자산 차단, 라이브 추가 scope·회수 |
| 물리 설치 | 최종 OS·CPU, 재부팅 자동 복구, NAS 정전·백업·회선·실제 마운트 |
| 성능 | 최대 동시 분석·녹화·라이브·복제 중 지연·유실·디스크·대역폭 |
| 운영 | 경보 수신, outbox·미복제 감시, 로그 접근, 복원 절차, 담당자 |

현장과 사무실이 동시에 사본을 잃거나 현장 보관 기간 밖 클립이 NAS에만 있으면 별도 NAS 백업 범위에 의존한다. main 승격과 운영 배포는 검수 결과와 해당 릴리스의 명시적인 사용자 승인이 필요하다. 현재 소스 구현·로컬 검증과 실제 설치·AWS 배포 상태는 별도로 보고한다.

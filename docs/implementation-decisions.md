# 구현 결정

## 실행과 저장

Python 3.12를 백엔드와 Linux 엣지의 공통 기준으로 사용한다. FastAPI 앱을 Mangum으로 Lambda 이벤트에 연결하며, 로컬에서도 같은 라우트와 업무 로직을 실행한다. 인증 검증기는 테스트에서만 주입한다.

DB는 PostgreSQL 17을 선택했다. 이벤트·자산 연결·초기 클립은 하나의 트랜잭션으로 저장한다. 이벤트 ID의 PostgreSQL 트랜잭션 잠금과 영상 작업 행 잠금을 사용해 활성 작업 생성과 lease 갱신을 직렬화한다. SQLite는 로컬 테스트 및 엣지 서버 저장에만 사용하며 운영 백엔드 설정에서 거부한다. 실제 배포의 PostgreSQL minor 버전은 리전 지원 여부를 확인한다.

DB 계정은 마이그레이션·등록을 수행하는 운영 계정과 API 실행 계정으로 분리한다. 실행 계정은 자산·권한을 읽기만 하고 heartbeat 열 및 이벤트·작업 데이터에 필요한 쓰기만 수행한다.

## 영상 큐와 복구

설치마다 별도 SQS 큐를 둔다. 여러 센터의 작업이 하나의 큐에 섞여 다른 엣지 서버가 반복해서 가져가는 상황을 피하기 위한 구성이다. 큐 URL은 백엔드의 엣지 서버 등록 정보에만 보관한다.

작업의 dispatch version과 DB 전송 표식을 이용해 DB 저장 후 SQS 전송 전 장애를 복구한다. DB 상태가 기준이며 SQS는 배정 전달에 사용한다. 큐 전달이 중복되어도 작업 행 잠금과 현재 시도 번호·토큰 해시로 유효 lease를 하나만 발급한다. 유지보수 함수는 미전달 작업, lease 만료와 접근 보관 만료를 처리한다.

시도별 객체 키는 서버가 정하며 업로드 조건은 같은 시도 안에서 바꿀 수 없다. S3 PUT에는 크기·형식·SHA-256 조건을 서명한다. 완료는 HEAD의 실제 크기·형식·ChecksumSHA256으로 확인한다. 해시가 같아야 하므로 발급된 PUT URL 재사용으로 다른 영상으로 교체할 수 없다.

이전 시도의 객체는 해당 작업의 마지막 PUT URL이 만료된 뒤 정리한다. READY 영상은 접근 보관 만료 후 정리하며 삭제 성공 시각을 저장한다. Lifecycle의 3일 규칙은 정리 누락에 대비한 보조 장치다.

## 현장 범위

현재 엣지 서버의 지원 실행 환경은 Python 3.12가 설치된 POSIX 호스트이며 운영 서비스 예시는 Linux systemd다. Windows 서비스 지원을 구현한 것으로 표시하지 않는다. 사무실 수신기는 운영자가 마운트한 NAS의 서비스 전용 영역에 쓰고, 현장 field는 생산 파일 루트를 읽어 자체 cacheRoot에 관리 사본을 확정한다. 사무실 마운트는 별도 볼륨 식별 마커로 확인한다. 열린 디렉터리 descriptor를 기준으로 파일을 찾아 심볼릭 링크와 경로 교체를 통한 루트 이탈을 막는다.

outbox·manifest·입력 receipt는 SQLite WAL과 FULL 동기화로 저장한다. 전송 중 종료된 건은 같은 ID·본문으로 복구하며 클립 갱신은 이벤트 ACK 및 이전 revision ACK 이후에 전송한다. 로컬 접수와 서버 ACK를 분리한다. 녹화·AI 모델의 사건 식별은 생산 프로그램의 책임이며 엣지 서버는 수신한 incidentId를 보존한다.

## AAS 범위

API 계약 버전은 3.1.2로 유지한다. Shell과 Submodel은 고정된 IDTA metamodel JSON Schema 3.1.2로 검증한다. Nameplate·TechnicalData의 실제 값은 등록한 자산 메타데이터에서만 가져오며 TimeSeries는 같은 이벤트 DB의 통계와 인증된 이력 URL을 제공한다.

현재 구현은 규격서에 나열된 읽기 경로의 부분 집합이며 전체 IDTA 서비스 프로파일 충족을 선언하지 않는다. `/description`의 `profiles`는 빈 배열이다. `properties-v1.json`은 프로젝트의 고정 필드 매핑이며 공식 IDTA Nameplate·TimeSeries 템플릿 전체 구현이라는 의미가 아니다. 실제 소비자와의 프로파일·semanticId 합의는 등록 매니페스트에 반영한다.

## 배포 경계

SAM 앱 스택은 기존 VPC·사설 서브넷·PostgreSQL 런타임 secret·ACM 인증서·Route 53 zone을 입력받는다. 선택적인 DB 스택은 같은 VPC에 사설 RDS를 만든다. 회사 네트워크와 운영 연락처는 임의로 생성하지 않는다.

직원용 public client는 secret 없이 code flow를 사용한다. 로그인 클라이언트는 PKCE를 적용해야 한다. 회사 SAML/OIDC IdP는 회사 제공 메타데이터로 연결한다. 초기 파트너·엣지 서버 client 외 설치를 추가하면 별도 client·큐를 만들고 allowlist와 DB 등록을 함께 갱신한다.

## 사무실 복제와 장애 전환 v1.2

이벤트 발신 설치와 업로더를 분리하고 검증된 사본을 센터·연결 자산 권한으로 배정한다. 기존 설치의 DB 역할 기본값은 legacy이며 현재 이력과 실행 계약을 보존한다. 새 field·archive 역할은 별도 client와 큐를 사용한다. 사무실 프로세스는 호스트 PC 또는 POSIX·Python 지원 NAS 내부에서 실행할 수 있다.

현장 관리 사본을 별도로 확정해 생산 프로그램의 파일 교체·정리와 업로드를 분리했다. 따라서 생산 프로그램 원본과 관리 사본을 같은 디스크에 두면 둘의 공간이 필요하다. 생산 프로그램 원본의 정리 정책은 생산 프로그램 운영자가 정한다. 관리 사본은 기본 30일 경과, NAS 실제 바이트 재검증, 서버 retire 및 작업 보호 확인 후에만 삭제한다.

클립 전송은 source가 요청한 제한 시간의 개별 전송 토큰을 사용한다. 수신기는 자신의 M2M 인증으로 백엔드에 송신자·수신자·불변 메타데이터를 검증받는다. NAS 바이트는 Lambda를 통과하지 않는다. 사무실 주소의 호스트 allowlist와 TLS를 적용하고 전송 토큰은 URL·DB 원문·로그에 남기지 않는다.

파일 확정과 SQLite·PostgreSQL 사이에는 분산 트랜잭션을 도입하지 않았다. 불변 파일명, 크기·SHA-256, 단계별 영속 상태와 동일 요청의 재검증으로 중단된 단계를 조정한다. 실제 fsync·hard link 영속성은 NAS 장비 검수가 필요하다. 기존 서명 PUT의 시도별 키와 고정 해시, DB 행 잠금 및 dispatchVersion이 오래된 업로드를 차단한다.

주·예비가 동시에 고장 나거나 현장 보관 기간 밖 사본이 NAS에만 남으면 NAS 백업에 의존한다. 현장과 AWS 사이의 회선은 사무실과 독립적으로 연결해야 한다. 실제 NAS·현장 장비가 준비되기 전의 합성 데이터 시험은 물리 장애·부하·현장 설치의 완료 증거로 사용하지 않는다.
